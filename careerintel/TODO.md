# Project ToDo — Placement Intelligence

Native project ToDo management is unavailable in this environment; this file preserves the complete outcome criteria until native tracking is available. Checked items indicate that the configurable frontend behavior is implemented. The final integration item remains open because the supplied workspace has no backend source or API contract. The implementation plan is in [`plan.md`](./plan.md).

- [x] **Application structure and student flow:** Create a proper multi-page application with Overview, Student Profile, Placement Prediction, Skill Gap Analysis, Recommendations, Salary Prediction, What-If Analysis, Data Analysis / EDA, and Model Performance; provide clear navigation between these sections; maintain the currently selected student's information while navigating; implement the flow Student Selection → Student Profile → Run/Load Analysis → Placement Prediction → Skill Gap → Recommendations → What-If Analysis → Salary Prediction; students must not have to repeatedly enter the same information.

- [x] **Overview / Home:** Immediately explain what the system is analyzing and include project title, short system description, current student selector/search, student summary, placement probability, placement readiness score, target job role, top strengths, top skill gaps, number of recommended improvements, salary prediction if available, and quick navigation/actions to analyze the student. Do not show generic platform statistics unless actually calculated from the backend dataset. The overview must answer: “What does the system currently think about this student?”

- [x] **Student selection and structured profile input:** Provide search student, select student, view basic student information, load that student's complete analysis, and change student without refreshing the entire application. If the project supports entering a new student profile, provide a structured student input form organized into Academic (CGPA, Backlogs, Attendance, academic-performance-related fields), Experience (Internships, Projects, Certifications, relevant experience), Technical Skills (Programming, DSA, SQL, Web Development, Cloud, other available technical skills), Aptitude & Soft Skills (Aptitude, Communication, other available fields), and Career Target (Target role). Use appropriate input components rather than one huge form; do not invent unsupported fields.

- [x] **Student Profile page:** Show the complete profile of the selected student, divided into academic profile, technical profile, experience profile, aptitude profile, communication profile, and career target. Include visual representations where useful for skill levels, academic metrics, experience indicators, and profile completeness. Provide an obvious action to run/re-run analysis for the current student.

- [x] **Placement Prediction page and explainability:** Display the model's actual placement prediction: placement probability, prediction/result, risk interpretation, confidence-related information if available from the backend, model used, and important contributing factors. Include a “Why this prediction?” section with positive factors that help the prediction and negative factors that reduce it; these must come from existing model/explainability outputs, not manually written statements. Include relevant model evaluation information only where appropriate. Do NOT imply that the prediction guarantees placement. For important ML outputs, show model used, that prediction is generated from the current student profile, analysis timestamp if available, and whether the result is a model prediction or requirement-based calculation. Clearly distinguish ML Placement Probability, Placement Readiness Score, and Skill Gap Analysis; do not merge them into one unexplained number.

- [x] **Skill Gap Analysis and role switching:** Allow the student to select/change a target role and use existing role requirements from the backend. For every relevant skill show current level, required level, difference/gap, importance, and status. Make strong skills, adequate skills, skills needing improvement, and critical gaps easy to identify. Include a role-fit result generated from existing backend logic. Allow switching between roles and dynamically recalculate/display the appropriate skill analysis. Do not hardcode skill values.

- [x] **Skill comparison visualization:** Create a dedicated visual comparison of the student's current skills versus target-role requirements, using suitable horizontal comparison bars, skill comparison matrix, radar-style comparison, gap indicators, and/or priority indicators. Every value must come from the student's actual profile and role-requirement data; do not hardcode skill values.

- [x] **Recommendations page:** Generate recommendations from the existing recommendation engine, not generic unrelated advice. For each recommendation show skill/area, current level, required level, gap, priority, why it matters, recommended improvement/action, and expected impact if available. Organize recommendations by priority, including High Priority (critical gaps affecting the target role), Medium Priority (skills that would significantly improve readiness), and Low Priority (additional improvements).

- [x] **What-If Analysis page:** Let the student modify selected skill values and submit them to the existing backend/model logic; do not calculate what-if predictions independently in the frontend. Show original placement probability, updated placement probability, difference, skills changed, and effect of each change if the backend provides it. Communicate “What happens to my prediction if I improve these skills?”

- [x] **Salary Prediction page:** Show salary/package prediction only if the backend provides a valid prediction. Include predicted salary/package, prediction range if available, relevant input factors, model information, and appropriate explanation/interpretation. Do not present the prediction as a guaranteed package. If salary prediction is unavailable for a particular student/data condition, display an appropriate state instead of inventing a value.

- [x] **Data Analysis / EDA page:** Display actual EDA results generated from the project, including dataset overview (number of records, number of features, target distribution, missing values, data types); student analysis (CGPA distribution, skill distributions, internship distribution, project distribution, placement distribution, relevant relationships/correlations); and important findings from the actual analysis. Charts should be interactive where practical. Do not fabricate findings.

- [x] **Model Performance page:** Display actual ML evaluation results: classification accuracy, precision, recall, F1-score and ROC-AUC; regression MAE, RMSE and R²; available models and their actual performance. Include model comparison table, confusion matrix, ROC curve, calibration information if available, and feature importance / permutation importance if available. Use actual generated model artifacts/results; do not manually enter metric values into the frontend.

- [x] **Loading, empty, error, and transparency states:** Implement loading states whenever student analysis is running, model prediction is being generated, skill-gap analysis is being calculated, what-if analysis is running, or data is loading. Every page must handle unavailable data, including no student selected, prediction not generated, salary prediction unavailable, no skill gap found, no recommendation available, and model evaluation data unavailable; never show fake values just to fill the UI. If backend/model/API fails, clearly tell the user analysis could not be loaded, provide a retry action, preserve selected student information where possible, and do not expose raw Python exceptions or backend stack traces to normal users.

- [x] **Responsive reusable UI:** Ensure the frontend works properly on laptop, desktop, and tablet, and analytical sections remain readable as the screen changes size. Build reusable components for student selector, metric cards, skill indicators, prediction result, recommendation item, skill-gap item, comparison chart, model metric table, empty state, loading state, error state, section headers, data tables, and filters. Avoid duplicating UI code across pages.

- [ ] **Inspect and integrate the actual backend without guessing:** First inspect the existing backend/API/model structure and identify available endpoints, input fields, output fields, prediction functions, skill-gap functions, recommendation functions, salary-prediction functions, what-if functions, and existing generated charts/results. Then connect the frontend to those existing functions/endpoints. Do not assume endpoint names or response formats. If an existing backend function already performs an analysis, use it instead of recreating that logic in the frontend. The frontend is a visualization and interaction layer: collect → send → receive → explain → visualize → interact; it must never hardcode → pretend → display. No source/API contract was supplied with the brief, so this outcome remains unresolved until backend source/repository or API base URL plus OpenAPI/endpoint documentation is available; meanwhile the configurable frontend must clearly show that it is not connected and must not fabricate data or claim integration is complete.
